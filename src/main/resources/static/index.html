Media path: ClamAV scans the uploaded original before extraction or transcription. Supported audio/video is sent to Infomaniak Whisper only after a clean scan; the resulting transcript is screened before approval. Direct text submissions have no uploaded file to scan. Detection or scanner outage blocks processing. Offline mode cannot screen or transcribe.

From input text to index: new text is screened before it waits for workspace-owner approval. After approval, the app splits it into chunks of up to 800 estimated tokens with a 100-token overlap. Each chunk's text and embedding vector, plus its embedding-model ID, are stored in PostgreSQL/pgvector with a full-text index; the original uploaded file remains in RustFS. Embeddings represent text as numbers for similarity search—they do not generate answers.

Text sent to AI models

Document screening classifier

  • Before approval, the structured-output model flags up to eight concrete statements in categories such as impersonation, payment redirection, credential requests, suspicious links, or malware/executable delivery. The app verifies each quote against the screened text and derives its source location. These are review cues, not a fraud or safety verdict; no findings do not prove a document is safe, and a workspace owner must still approve it. Screening is unavailable offline and fails closed.

Embeddings

  • Indexing sends approved text chunks to the embedding model; search sends the user's question or planned search query to that same model.
  • The model returns vectors. It does not receive a request to write an answer.
  • The configured dimensions must match both the embedding model's output and the PostgreSQL vector column. This pgvector halfvec HNSW setup supports at most 4,000 dimensions. Changing dimensions requires a compatible database schema migration and re-embedding indexed chunks.
  • Embedding reindex updates vectors for existing chunks; it does not change chunk boundaries. To apply a changed chunk size or overlap to existing documents, reprocess those documents.

Agent planner

  • Agent mode sends the question and metadata (IDs, filenames, and types) for up to 100 indexed workspace documents.
  • Document contents are not sent to the planner.

Reranker

  • After PostgreSQL combines full-text and vector results, a separate reranking model receives the question and up to 20 candidate passages and orders them by relevance. The top five then become answer context. It selects evidence candidates; it does not write the answer or verify that claims are true. Deterministic offline mode uses pass-through ranking.

Answer and grounding

  • The answer model receives the question and selected passages.
  • The grounding checker receives the question, draft answer, and those passages.

Optional invoice extraction

  • When requested, the extractor receives the selected document's text; extraction does not change its index.

Who chooses the harness and tools? The application developer selects the model and defines the harness: its prompt, allowed actions, validation, and execution loop. The planner model proposes a bounded plan; it cannot discover or run arbitrary tools. The backend validates the plan, enforces workspace access, and runs only the read-only search/comparison actions shown above. Offline mode uses one fixed search query unless the optional local Ollama planner is explicitly enabled. Regular chat bypasses the agent planner.

Application & access

  • Browser UI: chat, uploads, workspaces, job status, sources, and feedback
  • Keycloak: OIDC login and realm roles
  • Spring Boot / Spring Security: REST APIs, services, sessions, CSRF, and request authorization
  • Workspace membership: tenant isolation applied to document and search operations

Files & data

  • RustFS: S3-compatible originals
  • ClamAV: private Compose service scans uploaded originals before extraction or transcription; detections and scanner outages stop processing
  • PostgreSQL: workspaces, documents, durable jobs, and feedback
  • pgvector + PostgreSQL full-text: vector and lexical indexes
  • PDFBox 3 / UTF-8 reader: text extraction before chunking

AI services

  • Embeddings: index chunks and questions using the same configured model
  • Reranker: reorders retrieved candidates before answer generation
  • Chat model: grounded answers and structured invoice extraction
  • Planner and document screening: Infomaniak uses its structured-output planner model; Local Ollama uses Gemma for both; offline mode screens fail-closed
  • Whisper transcription: optional provider path for supported media

Guardrails & usage

  • Question validation: question is required and limited to 10,000 characters; unsupported answer modes and oversized filters are rejected.
  • Denied-topic policy: optional comma-separated phrases are matched case-insensitively before planning or retrieval; a match rejects the request.
  • Authentication & workspace: APIs require an authenticated user; browser state-changing requests require CSRF protection, and document access is checked against workspace membership.
  • Request limits: 30 direct queries and 10 agent runs per minute per client address, plus a 300-request per-minute client-wide limit; limits are in-memory for this single-instance deployment.
  • Provider PII masking: Infomaniak text inputs and generated answers are checked for email addresses, formatted phone numbers, and Luhn-valid payment-card numbers and masked when detected. This pattern-based check is not comprehensive; Whisper media transcription is excluded.
  • Prompt boundary: retrieved passages are treated as untrusted data, not instructions. There is no separate prompt-injection classifier.
  • Planner validation: structured planner output must match its strict schema; search count and query bounds are checked, and comparison IDs must identify distinct, indexed, supported documents in the active workspace.
  • Tool scope: agent tools are read-only, operate only on workspace documents, and run at most 3 planned searches; arbitrary SQL, writes, and external actions are unavailable.
  • Answer grounding: Infomaniak and Local Ollama answers receive a second structured model check and abstain when support is not confirmed; offline mode uses a deterministic passage-membership check.
  • Completion length: Infomaniak chat calls have a configurable completion-token ceiling (default 512, maximum 8,192); it does not cap input, embeddings, reranking, transcription, or total cost.
  • Invoice extraction: structured output is checked for allowed fields and valid types, dates, amounts, and source quotations; review extracted values before use.
  • Upload validation: uploads are limited to 20 MiB and checked by file signature or strict UTF-8 rather than trusting the supplied MIME type; each user has 1 GB object and indexed-data quotas aggregated across workspaces.
  • Not implemented: comprehensive PII detection, general-purpose moderation, distributed rate limits, and a monetary cost cap.
  • Document review: findings include exact quotations, validated extracted-text locations, indicator categories, and uncertainty or missing context; the model does not issue a fraud/safety verdict, and workspace-owner approval is required.
  • Malware: ClamAV scans original uploaded bytes before extraction or transcription; detections and scanner outages block further processing. A clean scan does not prove a file is safe.

Operations & boundaries

  • Compose initializers: create the S3 bucket and initialize the Keycloak realm account
  • Cloudflare Tunnel: optional public hostname routing to app and identity endpoints
  • Portainer CE: optional container management UI, loopback-bound
  • Public demo: separate fictional showcase; no workspace storage or model calls

What the agent does: For each question it plans focused searches, can compare two indexed documents when requested, combines evidence, then answers with citations. It cannot change or delete files, run arbitrary SQL, or call invoice extraction. Comparison is an exact paragraph diff, not semantic analysis. In offline mode, planning is deterministic unless the optional local Ollama planner is enabled. Tool steps and sources appear under each agent answer.

Structured extraction is a different task from RAG. Invoice extraction returns typed fields with quotations and deterministic plausibility warnings. It does not reconcile tax or line items; review consequential results.
