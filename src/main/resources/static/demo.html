Short learning guide

An AI application is more than a model. It prepares knowledge, finds relevant evidence, asks the model for a bounded task, and checks what can be checked. Each layer addresses a different failure.

  1. Prepare onceFiles → extracted text → passages → indexes
  2. Ask each timeQuestion → search → evidence → answer
  3. Check alwaysAccess → validation → evaluation → oversight
Why RAG? Motivation and the basic idea

A language model generates plausible text from what it learned during training and the prompt it receives. It may not know your private documents, recent changes, or the exact policy you need. RAG—retrieval-augmented generation—searches an approved knowledge collection first, then gives selected passages to the model as evidence for this answer.

Connection: retrieval supplies information; generation explains it. RAG does not retrain the model, guarantee truth, or make a weak source authoritative. You still need source ownership, freshness, and a way to verify claims.

Why index documents before asking questions?

Indexing is preparation done once per document: keep the original, extract text, split it into passages, attach source and access metadata, and build search structures. For semantic search, an embedding model turns each passage into a vector. A lexical index separately supports exact words and identifiers.

Why passages? Sending whole collections is slow, costly, and can exceed the model's context limit. Focused passages make retrieval precise and let the answer point back to evidence. Chunk size, overlap, extraction quality, and metadata all affect what can later be found.

Semantic search, lexical search, and hybrid retrieval

Semantic search compares vectors so “car” may find a passage about “automobile” even without an exact word match. Lexical search is often better for exact names, error codes, dates, and quoted phrases. Hybrid retrieval combines both signals; a reranker can then reorder the candidates against the full question.

Important limit: a reranker cannot recover evidence that the first search missed. Embeddings for stored passages and questions must use compatible models and dimensions. Measure retrieval quality on representative questions instead of assuming semantic similarity means relevance.

What “reasoning” can we inspect?

Do not treat a model's fluent explanation or hidden chain-of-thought as a reliable audit log. A safer learning trace shows observable steps: the question, which sources were retrieved, what context was supplied, which tools ran, what structured result was returned, and which validations passed or failed.

For a RAG answer: inspect the cited passage and ask whether it actually supports each important claim. A citation is a lead to evidence, not proof that the answer is correct.

Why guardrails? Security and reliability belong in layers

Prompts guide a model; they are not an access-control system. Authenticate users and filter documents before restricted content reaches retrieval or the model. Validate file types, input size, workspace ownership, output schemas, tool permissions, and resource limits in application code.

Why layers? Documents and tool results are untrusted data and may contain misleading instructions. Least-privilege tools, explicit approval for consequential actions, timeouts, rate limits, audit records, and tests reduce different risks. No single “guardrail prompt” covers them all.

Why JSON and schemas?

JSON gives software a predictable structure: named fields, numbers, arrays, and explicit missing values. A schema lets the application reject malformed output, enforce required fields, and pass valid data to the next step without guessing how to parse prose.

But: valid JSON proves only that the shape is valid—not that a value is true. Check values against source evidence and business rules; represent uncertainty and missing information explicitly rather than filling gaps with guesses.

Extraction models: typed values, not RAG answers

An extraction model returns named, typed values that an application can use. Depending on the model, a task can extract a value stated in the input, compute a value from supplied facts, estimate an unknown outcome, or forecast a sequence over time. For example, an invoice workflow could extract a due date, calculate days overdue from a supplied current date, or estimate when payment may arrive.

How it differs from RAG: RAG finds relevant passages and generates an answer grounded in them; extraction targets specific fields for application logic. A typed result, constraint, confidence score, or source span helps validation and review, but none guarantees correctness. Handle missing values explicitly and require stronger checks or human review when mistakes have consequences. Capabilities and uncertainty signals vary by model.

Tools, agents, and MCP are related—but not the same

A tool is a specific operation an application allows a model or workflow to request, such as searching an approved index or creating a draft. The application validates arguments, checks permissions, executes the operation, and returns a bounded result. An agent is a control loop that may choose among tools and continue from their observations.

MCP (Model Context Protocol) is a standard way for AI applications to discover and call tools or access resources provided by MCP servers. It is a connection protocol, not an agent, a security boundary, or a guarantee that a tool is safe. The host still needs authorization, allowlists, validation, and human approval where appropriate.

Common challenges and how to evaluate them
  • Bad source or stale version: govern ownership, dates, and replacement.
  • Extraction or chunking loss: inspect parsed text and test boundary cases.
  • Missed or irrelevant retrieval: measure recall and relevance separately.
  • Unsupported answer: verify citations and test abstention on unanswerable questions.
  • Access leak or unsafe action: test identity filters and tool permissions independently of prompts.
  • Slow or costly pipeline: measure latency and provider usage at each stage.

Evaluation should locate the failing stage. Improving the prompt will not fix a missing source, and adding a larger model will not repair an incorrect permission filter.

    Explore how a live RAG system works Architecture overview

    Behind the answer

    A complete RAG pipeline

    Illustrative architecture

    A live assistant prepares documents once, then retrieves the most useful evidence for each question. Each step solves a different problem; skip one and answers can become harder to find, less reliable, or impossible to verify.

    01 Prepare knowledge · indexing happens when documents are added

    1. Upload & authorizeBrowser · Keycloak · workspace

      Checks who is uploading and which workspace they may use. This keeps one user's documents separate from another's.

    2. Keep the originalRustFS · S3

      Stores the source file durably, so it can be reprocessed and the answer can point back to the original document.

    3. Queue an indexing jobPostgreSQL · job status

      Tracks progress and failures outside the upload request. Large files can be processed reliably without making the browser wait.

    4. Extract readable contentSpring Boot · PDFBox · optional transcription

      Turns supported files into text. Audio transcription is used when enabled; retrieval needs text to search.

    5. Split into passagesUp to 1,500 characters · overlap

      Creates focused, manageable pieces while overlap preserves context across boundaries. Smaller passages make evidence easier to find.

    6. Embed each passageInfomaniak AI · embeddings

      Maps meaning to a numerical vector. Similar ideas can then match even when a question uses different wording.

    7. Save text & vectorsPostgreSQL · pgvector · full-text index

      Keeps passages, vectors, document references, and workspace ownership together for fast, scoped retrieval later.

    02 Find a grounded answer · repeated for each question

    1. Ask & check accessBrowser · Keycloak · OIDC

      Receives the question and verifies the signed-in user's workspace before searching private content.

    2. Embed the questionSame embedding model

      Converts the question into the same vector space as the passages, making semantic comparison possible.

    3. Retrieve candidatesHybrid search · pgvector + full text

      Combines meaning-based search with exact word matching. This helps find both paraphrases and important names or terms.

    4. Rerank for relevanceBAAI/bge-reranker-v2-m3

      Scores candidate passages against the full question and moves the strongest evidence to the top.

    5. Build focused contextBest-matching passages

      Selects a small set of relevant evidence for the model. Focus reduces distraction and keeps the prompt within its limits.

    6. Generate from evidenceInfomaniak AI · chat LLM

      Uses the question and retrieved context to draft a response. The current app abstains when retrieval returns no passages; if irrelevant passages are returned, it may still generate an answer.

    7. Return answer & sourcesPassages → browser

      Includes document and passage references so a person can check where the answer came from.
